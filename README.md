## Задание 1. "Будильник" - анализ требований и тест-дизайн
### Пробелы и противоречия
1. **Snooze на N минут** - чему равно N? Данный параметр задается глобально (в настройках) и/или отдельно для каждого будильника? Это фиксированное значение или его можно менять во время срабатывания будильника?
2. **Конфликт типов будильников** - в первом требовании описан "базовый" будильник, во втором требовании указано, что будильник может быть **одноразовым** (срабатывает один раз в указанную дату) или **повторяющимся** (срабатывает каждые выбранные дни недели), как идет разграничение типов? Например, в чем разница между базовым будильником с вариантом срабатывания "каждый день" и повторяющимся будильником, у которого выбраны все дни недели? По сути базовый будильник дублирует функционал повторяющегося
3. **Обработка часовых поясов и смены системного времени** - что происходит при смене часовых поясов/переходе на летнее-зимнее время? Время срабатывания будильников привязано к локальному времени устройства или к абсолютному (UTC)?
4. **Формат ввода времени** - в каком формате вводится время? Визуальный элемент? Ручной ввод? Отдельный или единый ввод часов и минут?
5. **Что происходит после 5-го snooze** -  кнопка пропадает, будильник звонит до ручной остановки или останавливается сам?
### Приоритезированный чек-лист (Smoke-критерии)
1. **\[P0\] Создание будильника** - создание одноразового будильника, который должен сработать через 1 минуту
2. **\[P0\] Snooze функционал** - создание одноразового будильника, проверить, что откладывание сработает ровно заданное кол-во раз

4. **\[P0\] Автоотключение одноразового будильника** - создание одноразового будильника, проверить, что после срабатывания будильник перешел в неактивное состояние
5. **\[P1\] Повторяющийся будильник** - создание повторяющегося будильника, проверить, что после каждого срабатывания будильник остается активным нужное кол-во раз
6. **\[P1\]Переключение состояния** - проверить, что активный будильник переходит в неактивное состояние и наоборот
7. **\[P1\] Срабатывание в фоном/заблокированном состоянии** - проверить, что будильник срабатывает при заблокированном экране телефона
8. **\[P1\] Срабатывание в беззвучном режиме** - проверить, что будильник срабатывает в беззвучном режиме телефона
### Техники тест-дизайна
#### Классы эквивалентности и граничные значения
**Объект тестирования** - поле ввода времени (ЧЧ:ММ)
**Классы:**
- Позитивные - от 00:00 до 23:59 включительно
- Негативные - больше 23 для часов, больше 59 для минут, отрицательные для обоих полей
**Граничные значения:**
- Для часов: -01, 00, 01, 23, 24, 25
- Для минут: -01, 00, 01, 59, 60, 61
**Итоговые проверки:**

| --------------------- | ---------------------------------- |
| 00:00                 | Позитивный                         |

| 01:00                 | Позитивный                         |
| 22:58                 | Позитивный                         |
| 23:59                 | Позитивный                         |
| 24:00                 | Негативный (уточнить по вопросу 4) |

| −01:00 / 12:−01       | Негативный                         |
| пусто, `ab:cd`, `7:5` | Негативный (если ввод ручной)      |

#### Диаграмма состояний / use-case
**Состояния будильника:** Выключен, Запланирован, Звонит, Отложен (snooze).

| Из состояния | Событие                 | В состояние       |
| ------------ | ----------------------- | ----------------- |
| Выключен     | включить                | Запланирован      |
| Запланирован | выключить               | Выключен          |
| Запланирован | наступило время         | Звонит            |
| Звонит       | snooze (счётчик < 5)    | Отложен           |
| Отложен      | прошло N минут          | Звонит            |
| Отложен      | выключить               | Выключен          |
| Звонит       | stop, одноразовый       | Выключен          |
| Звонит       | stop, повторяющийся     | Запланирован      |
| Звонит       | нет реакции             | ? (не определено) |
| Звонит       | snooze при счётчике = 5 | ? (не определено) |
**Цепочки переходов:**

1. Запланирован → Звонит → snooze ×5 → Звонит → stop → Выключен (одноразовый). Проверить счётчик и итоговое состояние.
2. Запланирован → Звонит → snooze → Отложен → пользователь выключает будильник → отложенный звонок не срабатывает.
3. Повторяющийся: Звонит → stop → Запланирован, дата следующего срабатывания верна.

### Тест-кейсы API
#### Успешное создание заказа
Предусловия:
- Пользователь `user_id = 1` - существует
- Товар `product_id = 1` - существует, кол-во >= 5
- Сервис остатков доступен
Запрос - `POST /orders`
Тело запроса:
```JSON
{
	"user_id": 1,
	"items": [
		{
			"product_id": 1,
			"quantity": 5
		}
	]
}
```
Ожидаемый результат:
```JSON
201 Created

{
	"order_id": 1,
	"status": "created"
}
```
#### Некорректные данные
Предусловия:
- Пользователь `user_id = 1` - существует
- Товар `product_id = 1` - существует, есть на складе
- Сервис остатков доступен
Запрос: `POST /orders`
Тело запроса:
```JSON
{
	"user_id": 1,
	"items": [
		{
			"product_id": 1,
			"quantity": 0
		}
	]
}
```
Ожидаемый результат:
```JSON
400 Bad Request
```
#### Сервис проверки остатков недоступен
Предусловия:
- Пользователь `user_id = 1` - существует
- Сервис остатков недоступен
Запрос: `POST /orders`
Тело запроса:
```JSON
{
	"user_id": 1,
	"items": [
		{
			"product_id": 1,
			"quantity": 2
		}
	]
}
```
Ожидаемый результат:
```JSON
503 Service Unavailable
```
### Проверка результата
Статус запроса не гарантирует полное соответствие результата ожиданию - данные могли сохранится в неверном формате, неправильно отработала бизнес логика (например при создании заказа, на складе отсутствуют указанные товары, а заказ создался) и т.д.

Нужно проверять:
- Тело ответа - есть все поля, они корректны и соответствуют реальности
- При негативном сценарии заказ не создан
- Побочные данные - остатки списаны в нужном кол-ве, выполнены все смежные действия
### Бонусный вопрос
Возможные проблемы:
- Заказ создался дважды
- Ложный 409 на второй заказ - первый заказ зарезервировал последние товары, на второй заказ не хватило
Вопросы команде:
- Есть ли проверка уникальности заказов?
- Как обеспечена атомарность операций и защита от гонок при резервировании товаров на складе?
- Что происходит на сервере если пользователь разорвал соединение во время обработки заказа, не дождавшись ответа?
Проверить:
- Отправить два одинаковых запроса одновременно
- Эмулировать разрыв соединения во время обработки запроса, а затем повторить данный запрос
## Задание 3. SQL — базовые запросы
### Список пользователей из Москвы
```SQL
SELECT *
FROM users
WHERE city = 'Москва'
```
### Общая сумма оплаченных заказов по каждому пользователю, включая пользователей без заказов
```SQL
SELECT
	u.id,
	COALESCE(SUM(o.total), 0) AS paid_total
FROM users AS u
LEFT JOIN orders AS o
	ON u.id = o.user_id
    AND o.status = 'completed'
GROUP BY u.id
```
### Пользователи, у которых есть хотя бы один заказ со статусом returned
```SQL
SELECT
	u.id,
	COUNT(*) AS total_returned
FROM users AS u
JOIN orders AS o
	ON u.id = o.user_id
WHERE o.status = 'returned'
GROUP BY u.id
```
### Топ-3 пользователей по сумме оплаченных заказов
```SQL
SELECT
	u.id,
	COALESCE(SUM(o.total), 0) AS paid_total
FROM users AS u
LEFT JOIN orders AS o
	ON u.id = o.user_id
    AND o.status = 'completed'
GROUP BY u.id
ORDER BY paid_total DESC
LIMIT 3
```
### Пользователи не делавшие ни одного заказа
```SQL
SELECT
	u.id
FROM users AS u
LEFT JOIN orders AS o
	ON u.id = o.user_id
WHERE o.id is NULL
```
### Средняя сумма для одного заказа для всех оплаченных заказов для каждого города
```SQL
SELECT
	u.city,
    COALESCE(SUM(o.total)/COUNT(o.total), 0) AS avg_order_total
FROM users as u
LEFT JOIN orders AS o
	ON u.id = o.user_id
    AND o.status = 'completed'
GROUP BY u.city
ORDER BY avg_order_total DESC
```
